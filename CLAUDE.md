# DXV OS — project conventions

Spec: `DXV_OS_Product_Spec_FINAL.md`. Architecture overview: `README.md`.

- Blue is building this hands-on to learn: explain what you're doing and why as you go; ask before big, hard-to-reverse architecture calls.
- Palette is exactly `#fbe45b` (dxv-yellow), `#1a3c35` (dxv-green), white, black. Tints via opacity (`black/10`), never new colours. Warnings use yellow, not red.
- Domain rules go in `src/lib/pipeline.ts` (pure + unit-tested), not in components.
- Stage changes only via `moveVentureStage()` in `src/lib/ventures.ts` (past deals from the historical import: `importHistoricalDeclinedVentures()` there, which writes their stage history but no founder comms or lesson triggers).
- Every page and server action calls `requireAdmin()` itself; `src/proxy.ts` is not a security boundary. Pages may use `requireAdminWith(() => load())` to check and read in parallel; actions always check before writing.
- Speed: every database round trip costs ~80ms+ in production, so load a page's data in one `Promise.all` (Prisma `relationJoins` puts a record and its relations in one query); avoid sequential awaits.
- Angel logins (role `ANGEL`, one-to-one with an `Angel` record) see **only `/portal`** (its own layout: no team nav, Brain or job tray). Every portal page and action calls `requireAngel()` and touches only the signed-in angel's own record (id from the session, never from the form). `requireAdmin()` sends angels to `/portal`; every team API returns 401 to them. Partners are team members AND angels with ONE login (Blue, 2026-09-30): a team (`ADMIN`) login with `angelId` set also uses the portal as that angel (`requireAngel()` accepts it; header links "Member portal" / "Team app"; every team member sees "Member portal", and before their login is linked it opens `/member-access`, where they link their own angel record or create one, which makes it a Member), under the same statement and deal-room rules as every member. Angel-side tools (reset link, revoke, login-email sync) never touch a partner's login: that's managed on `/team`. The **Dashboard and Activity pages stay admin-only** (Blue). Ask Blue before exposing anything else to angels.
- **Deals are invisible to angels unless DXV explicitly shares one** (Blue, 2026-10-04), and then only while `canSeeLiveDeals()` is true: pitch deck from Member Pitch Selection; deck + memo (locked DXV Review Issue only, never AI drafts) + supporting documents from the post-pitch vote (Pitch Outcome); all applicable documents from Investment Commitments. The memo is the latest DXV Review Issue shown in full (as issued, including its scoring), never AI drafts or working drafts. Never eligibility screens, other AI output (AI-generated DD reports stay team-only), internal notes, other members' votes, or declined deals. The portal reads deals only through `src/lib/portal-deals.ts` (`loadDealRoom()`, `angelHasDealAccess()`); angel files go through `/api/portal/documents/[id]` (checked per request, each open logged as an `AngelEvent`). Sharing, the members' summary (`angelSummary`) and per-document `angelVisibleFrom` are set on the deal page's "Members' deal room" card and logged in `DealShareLog` (append-only). Angel votes are recorded as the signed-in angel into `PreSelectionVote` / `InvestmentVote`. From Due Diligence, documents marked `DUE_DILIGENCE` go only to members who committed to that deal (`committedAngelIds()`: latest live EOI interested, or a live Final Investment ticket; by `angelId` or confirmed alias) (Blue, 2026-09-30). AI-drafted DD reports (`ddReportJob`) are never shared: the team uploads a reviewed version.
- Team logins (role `ADMIN`): partners (Blue, Anna, Kevin) have equal access, including the Team page (Blue, 2026-09-30). Invites and password resets are one-time links from `/team` (`/join/team/<token>`, `TeamInvite`, hash only, 14 days); access is revoked/restored, never deleted; `teamRevokeBlock()` stops self-revoke and removing the last login; every step is logged in `TeamEvent`. A member (angel) login is given team access with `grantTeamAccess()` (same login, role becomes `ADMIN`); a team login is linked to an angel record with `linkTeamLogin()` (angel page). `scripts/create-admin.ts` is for bootstrapping only.
- Historical deals (`/deals/import`, rules in `src/lib/deal-import.ts`): older declined deals go straight to `PASSED` with their original dates and `importedAt` set; duplicates (by `normaliseCompanyName()`) are skipped. CSV imports share `ColumnMapper` (`src/components/column-mapper.tsx`).
- Onboarding: invite link (`/join/<token>`, one-time, 14 days, only its SHA-256 hash stored; also used for password resets while there's no email service) → set password + accept member terms → profile (confirm or answer questions) → investor statement (self-signed; records wording version, criteria, typed name, IP) or "neither applies" (portal without deals) → welcome. Steps are decided by `nextOnboardingStep()`. Every step is logged in `AngelEvent` (append-only).
- Legal wording angels see (`ComplianceText`: HNW and sophisticated statements, member terms) is versioned: bodies never change, edits are new drafts, and only an admin-approved version is shown or signed. Invites are blocked until all three are approved. Starting drafts in `src/lib/compliance-texts.ts` need Kevin's word-for-word check against the Financial Promotion Order.
- Append-only tables (StageChange, MemoVersion, PreSelectionVote, EntryAudit, PlaybookVersion, AngelCertification, AngelNote, AngelEvent, DealShareLog, TeamEvent): never add update/delete paths. EOIs (`InvestmentVote`) and `FinalInvestment` are editable (Blue, 2026-09-29) but every edit, payment tick and removal writes an `EntryAudit` row, and removal only sets `removedAt` (always filter `removedAt: null`).
- "Passed" is labelled **Declined** in the UI (enum stays `PASSED`; `passedFromStage` records where). Capital Transfer is retired. The board shows declined deals only via the Declined filter pill (read-only, grouped by `passedFromStage`); the live board has no Declined column; dropping a card on the Declined pill declines it (reason dialog). Investment Total = paid Final Investment tickets (`investedGbp()` in pipeline.ts).
- Forms use `ActionForm` (`src/components/action-form.tsx`); actions return `ActionResult`. Every clickable thing gives feedback: buttons use `buttonClass` / `SubmitButton` / `ActionButton` (spinner + working label, "✓ Saved" after); no bare `<form action>` buttons.
- Long AI jobs: call `announceJobStarted()` after starting one; the floating `JobTray` (`src/components/job-tray.tsx`, reads `/api/jobs`) shows progress and refreshes the page when done. Pages must not poll themselves (the one exception: the DXV Brain panel checks its own chat while a reply is being written).
- DXV Brain (`src/lib/brain/`, `src/components/brain/`): floating chat on every page, Claude Opus 5.5 (Blue's choice). It reads DXV OS through read-only tools and **never gets write tools** (Blue: "read everything, change nothing"). Chats are private per user: every chat query filters by `userId`. Brain messages store the exact API content and are replayed unchanged (append-only, so follow-ups keep context and caching works); never edit or reorder stored turns. The Brain's instructions and tools are fixed per chat (`BrainContext.setup`): to change either, bump `BRAIN_SETUP_VERSION` and branch on it so older chats keep theirs byte for byte (Claude rejects follow-ups if they change mid-chat). New Brain tools go in `tools.ts` as plain SQL (shared with the worker), behind a new setup version.
- Angels (`/angels`, `src/lib/angels.ts`, rules in `pipeline.ts`): certification and financial data are sensitive (admin-only routes, signed-URL files). The latest-signed `AngelCertification` counts; members without a current one "need certification" (the headline metric). `canSeeLiveDeals()` is the gate for future angel logins: enforce it server-side. Votes/investments link to angels by `angelId` (new entries) or a confirmed `AngelAlias` (older typed names): resolve with `resolveAngelId()`, never by editing old votes. Tags are self-declared only; no ethnicity field until Kevin confirms the lawful basis.
- Deal page layout follows the stage: `focusSections()` / `advanceTarget()` in `pipeline.ts` decide which sections start open ("Now") and where one-click Advance goes; other sections collapse (`Card collapse`). Entry forms sit behind `Reveal` ("+ Add…") buttons.
- Every page has a `loading.tsx` skeleton next to it (route groups keep one route's skeleton from showing for another).
- Helpers used by server components must not live in `"use client"` files.
- Client code that calls a server action outside `ActionForm`/`ActionButton` must catch errors with `actionErrorMessage()` (`src/lib/stale-version.ts`), so a page open across a deploy shows the Reload banner rather than a raw error.
- Prisma 7: client is generated to `src/generated/prisma` (import from `@/generated/prisma/client` or `/enums`). Scripts run via `tsx --conditions=react-server`.
- Deployed on Netlify + Supabase (`docs/DEPLOY.md`). Every migration that creates a table must also `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` (Supabase Data API exposure).
- Playbook (`/playbook`, `src/lib/playbook/`): DXV's eligibility and assessment criteria are team-edited, versioned content; the AI prompts are built from the latest version plus approved lessons (`aiContextFor()`), snapshotted onto each job (`DeckAnalysis.aiContext`, `MemoContext.ai`) so every screen/memo records the version it used. Version 0 = DXV's original documents, verbatim (a test proves the rebuilt prompts match exactly). Memos keep the criteria they were scored against: use `maxScore(scores)`, never a fixed /55. AI-suggested lessons (`lesson-triggers.ts`: declines, memo score overrides, eligibility disagreements) stay SUGGESTED until a person approves them; lessons are archived, never deleted.
- AI deck reading: model in `src/lib/deck-ai/prompt.ts` (prompt from the Playbook); the AI suggests, humans decide (never auto-move a deal on AI output). Decks dropped on the board's Submitted column are intake-only (`DeckAnalysis.intakeOnly`: name, founder, stage; `screen` is null), so "latest screen" lookups must require a screen. Modules shared with `netlify/functions/` must not import `server-only` or use `@/` aliases.
- AI memo assessment: model in `src/lib/memo-ai/prompt.ts` (prompt from the Playbook; version 0 is DXV's document, verbatim); the review banner is app-rendered, never model-generated. Naming: AI Draft N → DXV Review Draft N (one working draft per issue) → DXV Review Issue N (locked) → revise → Draft N+1 (helpers in `src/lib/memo-ai/render.ts`). AI drafts (`MemoAnalysis`) and issues (`MemoVersion`) are never edited; only `MemoDraft` is, and score overrides are logged.
- DD document: prompt in `src/lib/dd-doc/prompt.ts`, Word layout in `src/lib/dd-doc/build.ts`; the "DRAFT: AI-assisted" notice is app-rendered. Generated files are ordinary `Document` rows (category DUE_DILIGENCE), never overwritten.
- Exports: any document DXV OS creates gets `ExportLinks` (PDF + Word) via `/api/export/...`; describe it once as a `DocSpec` (`src/lib/export/`) so both formats match. PDFs use standard fonts (Windows-1252 only: `pdf.ts` swaps or drops other characters).
- Documents: DXV OS (Supabase Storage) is the document store; **no Google Drive links**. Nothing is deleted, declined deals included (Blue's decision, for dealflow learning); mistaken uploads are archived. Allowed types and limits live in `src/lib/documents.ts`.
- Before pushing: `npm test && npm run typecheck && npm run lint && npm run build`.
- PRs: Claude opens a PR for its work and may merge its own PRs once those checks pass (Blue's standing permission). Merging to `main` deploys to production and runs migrations, so always tell Blue what merged, and call out any database migration explicitly.
